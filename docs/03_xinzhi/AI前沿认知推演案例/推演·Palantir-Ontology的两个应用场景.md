# Palantir Ontology 的两个应用场景——为什么机场与 ICU 是「翻倍」而非「加分」

你的直觉很敏锐——机场、ICU/急诊室这类场景，恰恰是 Palantir Ontology 价值最容易被低估、也最容易被误解的地方。关键在于：你看到的“预案都有”是静态的知识，而 Ontology 要解决的是动态的决策执行。两者不在同一个层面上。

Ontology 的本质：不是知识库，是“决策的操作系统”

Ontology 在设计初衷上就是为了表示决策，而不仅仅是数据或知识。一套预案写在手册里是“死”的；Ontology 要做的是把预案中的对象（患者、床位、护士、航班、物料）、约束规则（“脓毒症患者须在1小时内用抗生素”）、行动（调度、分配、改派）全部建模成一个可以实时读写、可被 AI 直接调用的动态业务网络。当现实条件发生变化时，系统不是在“查阅预案”，而是在约束条件下实时重新计算最优行动，并把结果写回到操作流程中。

所以，已有预案非但不是障碍，反而是 Ontology 发挥价值的前提——没有预案，就没有可被形式化的“业务逻辑”；但只有静态预案，没有 Ontology，预案就无法在动态现实中实时“活起来”。

哪类场景会产生“翻倍”效果，而非“加分”效果？

“加分”和“翻倍”的差别，取决于一个核心变量：决策的频率与出错代价的乘积。

当一个场景同时具备以下三个特征时，Ontology 的效果倾向于翻倍甚至数量级，而不是线性改善：

① 数据极度分散，且“跨域协同”是瓶颈。 效果翻倍的场景，往往不是单一系统能解决的。英伟达的供应链物料分配，需要同时考虑数千家供应商、制造场地产能、运输中的物料持有时间、每周波动的供应状况，这些信息分散在互不关联的系统中。Ontology 把它们统一为“物料—场地—承诺—产能”的对象网络后，AI 才可能做出人类无法手工完成的分配决策，将准确率推至 86.7%，显著优于通用大模型。

② AI 需要“写回”行动，而不仅是给出建议。 只做分析看板的 AI，天花板是“加分”。Ontology 的核心能力之一是 Action 写回：决策一旦做出，直接在业务系统中改变状态、触发流程。空客将 A350 的交付速度提升了 33%，不是靠一个更聪明的报表，而是靠决策直接作用于生产与供应链动作。一家财富100强消费品公司通过 Foundry 的自主规划与执行方案，6个月内产生了超过 1 亿美元的价值，同样是因为决策闭环到了执行端。

③ 约束条件在实时变化，静态优化失效。 港口的船舶调度、航空公司的机组排班、能源管网的压力平衡，都属于“上周的最优解这周就失效”的场景。Kinder Morgan 的能源储运场景中，Ontology 将原本需要 2—3 小时的决策周期压缩到 2—3 分钟，改变的是决策的时间尺度本身，而非在原有尺度上挤效率。

你提到的机场与 ICU/急诊室：属于哪一类？

它们恰恰属于“翻倍”区间，而非“加分”区间。

急诊和 ICU 的典型特征是：资源（床位、护士、设备）刚性受限，需求（患者流入）不可预测，且每一次调度决策都直接关联临床结局。这正是 Ontology “资源约束下实时调度”的原生场景。在 Cleveland Clinic 的案例中，将患者、床位、人员、设备建模后，容量计算效率提升了 75%，转院率改善了 10%。Tampa General 的医院协同系统将患者安置时间降低了 83%，脓毒症住院日缩短了 30%。英国 NHS 也在用 AIP + Ontology 管理择期手术积压：当手术室因人员短缺空置时，系统自动建议患者改道或调整排班。

这些数字不是“比原来好一点”，而是在关键流程节点上改变了结果本身。急诊涌入大量患者时，Ontology 不是在“执行一套写好的分流预案”，而是在床位、护士、物资的实时约束下，重新计算此刻的最优分配方案并直接驱动行动。预案提供了规则框架，Ontology 提供了让规则在动态现实中持续生效的机制。

机场也是同理：航班延误的连锁反应（机组超时、后续航班衔接断裂、旅客误机）本质上是关联对象的级联更新问题。Ontology 把航班、飞机、机组、排班优化器建成相互关联的对象，一个延误事件自动触发关联对象的重新计算与写回，这是静态应急预案无法做到的。

一个务实的判断框架

如果非要把“翻倍”与“加分”分开，可以问三个问题：

决策是否横跨多个系统/部门，且协同成本是当前的主要摩擦？ 是 → 翻倍潜力；否 → 加分。

AI 的输出是否需要直接改变操作状态（写回），而非停留于洞察？ 是 → 翻倍潜力；否 → 加分。

外部条件的变化频率是否高到让静态优化/人工预案快速失效？ 是 → 翻倍潜力；否 → 加分。

反过来说，如果一家企业已有高度统一的数据平台，业务范围较窄，决策链条短且变化慢，Ontology 的增量价值确实会退回“选择性引入”的层面，更适合在局部场景试点。Palantir 自身也提示，Ontology 不是替代既有信息化建设的“神级系统”，它是一座桥——桥的价值，取决于两岸之间是否真的存在需要高频跨越的鸿沟。

所以，你看到的机场和 ICU 场景，预案的存在恰恰说明业务规则已经被充分认知，缺的不是“知道该怎么做”，而是“在动态约束下实时算出此刻最优的那一个做法，并让它发生”。这正是 Ontology 与 AI 结合后，从“加分”跨入“翻倍”的临界点所在。
